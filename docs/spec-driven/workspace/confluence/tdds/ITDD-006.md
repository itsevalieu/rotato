### 🛑 STOP — Question 2: Field value preservation on style switch

The ticket says "re-renders in the selected style without losing any partially-entered field values." The Feature TDD describes the container pattern but doesn't confirm whether this is a firm product requirement or an implementation nicety.

This is HIGH STAKES because it has a direct architectural consequence: if each style component manages its own state, switching re-mounts and resets. Preserving values requires lifting all field state to `ProjectForm`.

Options:
- **A: Lift state to `ProjectForm`** — all 6 components are purely presentational. Switching preserves values. More files affected (every form style must accept `FormStyleProps`). Better UX.
- **B: Per-component state** — simpler component design. Switching resets values. Breaks expected UX behavior.

**Resolution from Designer (Slack, 8 min turnaround):** "Definitely A. Someone filling out a form and switching to see how it looks should not lose what they typed. That would feel broken."

**Confidence:** 🟢 GREEN (Designer decision, documented)

## Problem

ROT-002 gave users one way to fill out the project form (Classic). ROT-006 gives them six. The core challenge: provide 6 visually distinct form experiences without duplicating state management, while persisting the user's style preference across sessions.

---

## Approach

1. Add `FormStyle` type and `formStyle` field to `GardenState`. Add `SET_FORM_STYLE` reducer action.
2. Create `FormStyleProps` interface — the shared contract all 6 style components receive.
3. Refactor `ProjectForm` as a container: it owns all field state and renders the active style component, passing `FormStyleProps` down.
4. Build 6 style components in `form-styles/`.
5. Build `FormStylePicker` — reads `state.formStyle`, dispatches `SET_FORM_STYLE`.
6. Pass `FormStylePicker` via `Modal`'s `headerAction` prop. Use `size="lg"` for Live Preview.

---

## Alternatives Considered

**Render-prop pattern instead of `FormStyleProps` interface:** More flexible in theory, harder to reason about in practice. Rejected — explicit interface is clearer for 6 known variants and easier to type-check.

**CSS-only switching (same DOM, different styles):** Not feasible. Each style has fundamentally different DOM structure (Envelope has SVG flap, TwoBeat is multi-step, LivePreview is split-panel). CSS alone can't accommodate these differences.

**Per-style form state (no lifting):** Simpler per-component. Rejected — Designer confirmed field preservation is required (Dead Reckoning resolution #2).
